# Frontend Observability Platform 开发排期

## 1. 项目定位

这是一个面向现代 Web 应用的轻量级可观测性平台，围绕前端业务事件采集、运行时错误追踪、性能监控和数据分析，构建一个完整的观测链路。

项目整体结构包括：
- Demo App：模拟被监控业务系统
- Analytics SDK：采集前端事件并上报
- Server：接收、校验与存储遥测数据
- Dashboard：统一查看事件、错误、性能、趋势
- Shared Types：定义协议与共享类型

本排期以“可演示 MVP + 稳定迭代”作为目标，适合 4~6 周的开发节奏。

## 3. Phase 1：基础设施与可运行性（第 1 周）

### 目标

建立项目的开发基线，保证所有模块都可以在本地跑起来，并为后续功能构建稳定上下游。

### 核心任务

1. 统一环境变量和本地依赖
   - 配置 `.env` 和 Docker PostgreSQL
   - 确保 `pnpm install` 能正常完成

2. 完成数据库初始化
   - PostgreSQL 容器启动
   - Drizzle schema 定义
   - migration 生成和执行

3. 启动服务端基础能力
   - NestJS app 正常启动
   - 健康检查接口 `/health` 正常返回
   - 基础 `AppController` 和 DB 连接就绪

4. 定义事件协议基础结构
   - eventId
   - timestamp
   - projectId
   - sessionId
   - eventName
   - eventType
   - properties

### 验收标准

- `docker compose up -d postgres` 成功
- `db:migrate` 成功执行
- `pnpm --filter @fe-observability/server start:dev` 能启动
- `/health` 返回 HTTP 200 且带状态字段
- 统一事件协议文档已形成

### 风险点

- 环境变量缺失导致服务端无法连接数据库
- Drizzle schema 和 migration 未同步
- 不同子项目使用不同 env 规范，导致测试与本地开发不一致

---

## 4. Phase 2：SDK 与 Demo App 事件采集（第 2 周）

### 目标

完成可观测性采集链路的前端侧能力，让 Demo App 能产生真实上下文信息，并把事件上报到后端。

### 核心任务

1. 设计 Analytics SDK
   - 统一 `capture` 方法
   - 支持页面访问事件
   - 支持业务事件上报
   - 支持错误日志采集
   - 支持性能指标采集

2. SDK 功能能力
   - 事件缓存与批量发送
   - 重试逻辑
   - 采样控制
   - 过滤敏感信息
   - 统一上下文（projectId、sessionId、environment、version）

3. Demo App 接入
   - 业务操作模拟：创建任务、执行任务、失败任务
   - 多页面访问模拟
   - JS 异常模拟
   - 性能指标触发

### 验收标准

- SDK 能在 Demo App 中正常初始化
- 页面访问事件成功上报
- 业务事件成功上报
- JS 异常事件成功上报
- 数据流到后端 API 里能识别

### 风险点

- 事件格式不统一，后端难以解析
- SDK 频繁上报导致页面性能下降
- 无网络或请求失败时未正确做缓存/重试

---

## 5. Phase 3：后端接收、校验与存储（第 3 周）

### 目标

把 SDK 发送的数据纳入服务端统一处理，确保数据能够被校验、落库和查询。

### 核心任务

1. 接收与校验 API
   - `POST /events`
   - 请求体 schema 校验
   - 项目识别与环境字段校验
   - 过滤非法或过大 payload

2. 持久化能力
   - events 表设计
   - project 表设计
   - 事件去重或幂等处理
   - 基础索引与查询字段准备

3. 查询接口
   - 按时间查询事件
   - 按项目、事件类型过滤
   - 聚合错误与性能数据

4. 后端稳定性
   - 限流
   - 失败重试
   - 错误日志接入

### 验收标准

- SDK 上报数据能入库
- 事件查询接口能返回结构化 JSON
- 错误请求会返回明确 4xx/5xx
- 基础项目和事件查询链路闭合

### 风险点

- 事件体积过大导致存储压力
- 后端字段校验过严导致正常事件被拒绝
- 缺少分页和聚合策略导致仪表盘查询性能差

---

## 6. Phase 4：Dashboard 可视化（第 4 周）

### 目标

构建一个可以演示和使用的 Dashboard，真实展示前端应用的事件、错误和性能情况。

### 核心任务

1. 项目管理页
   - 项目列表
   - 创建/切换项目
   - 环境选择

2. 事件概览页
   - 事件列表
   - 筛选器：项目、时间、事件类型、环境
   - 详情查看

3. 错误分析页
   - 错误列表
   - 分组统计
   - 错误占比和趋势

4. 性能分析页
   - Web Vitals 分析
   - 页面加载性能
   - 平均耗时和趋势图

5. 基础图表展示
   - 折线图
   - 柱状图
   - 饼图/分布图

### 验收标准

- Dashboard 可以查看项目和事件
- 关键图表能展示真实数据
- 错误页面和性能页面具备主流程
- 用户能在页面上进行过滤和切换

### 风险点

- 数据格式不一致导致页面渲染错误
- 各页面查询接口过多造成性能瓶颈
- 图表库选型不最佳，后续扩展困难

## 7. Phase 5：稳定性、测试与交付准备（第 5~6 周）

### 目标

提升工程质量，使项目具备可持续积累的能力，并为演示或上线做好准备。

### 核心任务

1. 测试覆盖
   - 单元测试
   - API 集成测试
   - e2e 脚本
   - SDK 回归测试

2. 稳定性增强
   - 重试策略与幂等处理
   - 采样和限流配置
   - 高并发上报保护
   - 内存和 CPU 监控

3. 文档与部署
   - README 更新
   - 架构文档完善
   - 数据库初始化说明
   - 部署脚本和环境变量文档

4. 性能和体验优化
   - SDK 上报开销优化
   - Dashboard 首屏优化
   - 查询接口优化

### 验收标准

- 测试覆盖核心功能
- 关键链路可以稳定运行
- 运行日志和错误处理机制齐全
- 可完成项目展示和交付说明

### 风险点

- 测试不足导致回归问题频发
- 采样与缓存策略不合理造成数据丢失
- 部署前未统一环境变量，导致上线失败

## 8. 建议的里程碑

### Milestone 1：环境成型（第 1 周）
- 本地开发环境可跑
- DB 可初始化
- 健康检查可用

### Milestone 2：试探型采集链路（第 2 周）
- Demo App 发送真实事件
- 后端能接受事件

### Milestone 3：数据闭环（第 3 周）
- 事件存储成功
- 查询接口可用

### Milestone 4：演示版 Dashboard（第 4 周）
- 页面能展示事件、错误和性能数据

### Milestone 5：稳定版 v1.0（第 5~6 周）
- 测试、稳定性和部署准备完成

---

## 9. 建议的实施方式

### 方式 A：MVP 版本（推荐）
适合快速验证产品方向，节奏更稳。
- 前 3 周完成事件上报和接收
- 第 4 周做 Dashboard 的最小可用版本
- 第 5~6 周做质量和优化

### 方式 B：功能全量版本
适合有充足时间和更复杂需求的情况，但会增加开发和协调成本。建议只在具备清晰需求和充分人员支持时使用。

---

## 10. 结论

这个项目的开发节奏应当遵循“先打通链路，再做可视化，再完善稳定性”的顺序：

1. 先把环境和数据库跑起来
2. 再让 SDK 真正采集数据
3. 再让后端稳定接收和存储
4. 再让 Dashboard 展示数据
5. 最后补测试和工程化能力

这样最符合这个项目的工程特点，也能最快形成可演示成果。
