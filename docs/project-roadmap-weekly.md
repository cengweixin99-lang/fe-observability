# Frontend Observability Platform 周任务排期

## 1. 总体目标

在 6 周内，完成一个可演示的前端可观测性平台 MVP，覆盖：
- 前端事件采集（页面访问、业务事件、错误、性能）
- 后端事件接收与存储
- 数据查询与展示
- 可视化 Dashboard

目标不是一次性做成完整平台，而是先打通从“埋点 → 上报 → 存储 → 展示”的关键链路，并保证工程基础稳定。

---

## 2. 时间线总览

| 周次 | 主题 | 关键成果 | 验收标准 |
| --- | --- | --- | --- |
| Week 1 | 项目基建与环境 | 本地环境、DB、健康检查、协议基础 | 可启动、可迁移、可健康检查 |
| Week 2 | SDK 与 Demo App 埋点 | 页面/事件/错误/性能采集 | 能上报真实数据 |
| Week 3 | 后端接收与存储 | API 接收、事件入库、查询接口 | 数据落库且可查询 |
| Week 4 | Dashboard 1.0 | 项目管理 + 事件列表 + 过滤 | 可看数据 |
| Week 5 | Dashboard 2.0 | 错误分析 + 性能分析 | 可演示核心分析能力 |
| Week 6 | 稳定性与交付 | 测试、优化、部署准备 | MVP 可交付 |

---

## 3. Week 1：项目基建与环境

### 目标

搭建本地开发环境，确保项目在单机上可完全跑起来。

### 具体任务

1. 环境统一
   - 确认 Node.js / pnpm / Docker 版本
   - 统一工作区脚本定义

2. 数据库与迁移
   - 启动 PostgreSQL 容器
   - 完成 Drizzle schema 初版
   - 生成并执行 migration

3. 服务端基础铺底
   - 健康检查接口 `/health`
   - NestJS app 启动正常
   - 基础错误处理与日志输出

4. 协议基础
   - 统一事件字段定义
   - 确认项目、环境、版本字段规则

### 交付物

- 可用 PostgreSQL 本地容器
- 可执行数据库 migration
- 服务端健康检查接口正常返回
- 共享类型或协议文档基础版本

### 验收标准

- `docker compose up -d postgres` 成功
- `db:migrate` 成功
- `pnpm dev:server` 可启动
- GET `/health` 返回 HTTP 200

### 风险

- 环境变量缺失
- 多应用共享 `.env` 方式不统一
- schema 与 migration 未同步

---

## 4. Week 2：SDK 与 Demo App 埋点

### 目标

让 SDK 具备真实采集能力，并把被监控应用的数据发到后端。

### 具体任务

1. SDK 基础设计
   - 初始化项目配置
   - 统一 `track` / `capture` 入口
   - 自动附加环境、session、时间戳

2. 埋点事件类型
   - `page_view`
   - `custom_event`
   - `error`
   - `performance`

3. Demo App 接入
   - 业务行为模拟：创建任务、执行任务、失败任务
   - 页面跳转触发访问事件
   - 异常场景触发 JS error

4. 上报链路
   - 本地缓存
   - 批量上报
   - 重试机制
   - 失败态处理

### 交付物

- 可用 SDK 包
- Demo App 可发送真实采集事件
- 后端接收到数据的最小链路验证

### 验收标准

- 页面访问事件能上报
- 业务事件能上报
- JS error 能上报
- SDK 在网络异常时不会直接丢失数据

### 风险

- SDK 与后端协议不一致
- 被监控 app 的默认页面不稳定造成埋点缺失
- 批量上报和重试导致事件顺序异常

---

## 5. Week 3：后端接收与存储

### 目标

把前端采集的数据从“传送”变成“可管理、可查询、可分析”的数据资产。

### 具体任务

1. API 开发
   - `POST /projects`
   - `POST /events`
   - `GET /events`
   - `GET /projects`

2. 数据落库
   - project 表
   - events 表
   - 基础索引建立

3. 数据校验
   - 事件结构校验
   - projectId 校验
   - 时间字段合法性
   - 大对象/非法字段过滤

4. 查询接口
   - 按时间范围查询
   - 按事件类型筛选
   - 按 project/environment 过滤

### 交付物

- 可接受 SDK 上报
- 可落库 events 数据
- 可以查询事件列表
- 可查看基础项目维度统计

### 验收标准

- SDK 上报请求返回 2xx
- 数据可进入 PostgreSQL
- 查询接口返回结构化 JSON
- 可定位某个项目或某个时间窗口的数据

### 风险

- 事件过大导致存储和解析问题
- 频繁写入造成数据库压力
- 查询接口缺少分页和过滤，会拖垮前端

## 6. Week 4：Dashboard 1.0

### 目标

搭建 Dashboard 的最小可用版本，让数据可视化展示出来。

### 具体任务

1. 项目管理页
   - 项目列表
   - 新建项目
   - 切换项目
   - 选择环境

2. 事件列表页
   - 实时/最近事件展示
   - 事件类型过滤
   - 时间筛选
   - 基础搜索

3. 统计面板
   - 总事件数
   - 今日事件数
   - 失败次数
   - 关键业务指标

4. 交互体验
   - 卡片布局
   - 表格展示
   - 基础图表

### 交付物

- Dashboard 可访问
- 能看到项目和事件数据
- 基础筛选功能可用

### 验收标准

- 用户能打开 Dashboard
- 一定数量事件能正常展示
- 过滤器生效
- 页面无明显渲染异常

### 风险

- 前端状态管理和接口节流不清晰
- 图表数据格式与返回结构不一致
- 大表格渲染会出现性能问题

## 7. Week 5：Dashboard 2.0 与分析能力

### 目标

补齐错误和性能分析能力，让平台真正具备“观测”价值。

### 具体任务

1. 错误分析页
   - 错误列表
   - 错误分组
   - 错误趋势
   - 关键堆栈信息

2. 性能分析页
   - Web Vitals
   - 加载耗时
   - 页面平均性能
   - 关键指标趋势

3. 业务分析基础能力
   - 按事件类型聚合
   - 业务 funnel 的基础替代方案
   - 时间维度对比

### 交付物

- 错误页有正式展示
- 性能页能看数据趋势
- Dashboard 已具备演示价值

### 验收标准

- 可按错误类型统计
- 可按性能维度查看趋势
- 可从 Dashboard 得到“业务状态判断”结论

### 风险

- 相关统计 SQL 或聚合逻辑复杂
- 事件量大时聚合性能较差
- 用户看板需要足够容易理解

## 9. 关键依赖关系

以下依赖必须按顺序落地：

1. 环境与 DB
2. 事件协议
3. SDK 埋点能力
4. 后端接收与存储
5. Dashboard 交互层
6. 分析能力
7. 稳定性与交付

如果任意一环没有打通，后续功能会出现“看起来能做、但无法闭环”的问题。

---

## 10. 建议的执行原则

### 1. 每周必须交付一个可运行版本
避免“代码写了一堆但没有演示结果”的情况。

### 2. 先做最短链路，再做复杂分析
MVP 重点是事件从前端到 Dashboard 的闭环，而不是一开始就做大而全的数据分析能力。

### 3. 以测试做保障
每个阶段结束前，至少保留一条关键链路的自动化验证。

### 4. 先技术验证，再做产品细节
先保证采集、存储和展示工作可靠，再补 UI 细节和分析复杂度。

---

## 11. 最终建议

如果按 6 周推进，建议采用以下优先顺序：

- Week 1：**打底**
- Week 2：**采集**
- Week 3：**存储**
- Week 4：**可视化**
- Week 5：**分析**
- Week 6：**稳定与交付**

这套节奏最稳，也最符合当前项目结构：
- Server 已经有 NestJS 骨架
- apps/demo-app 和 dashboard 都在布局中
- SDK 和 shared-types 也已经在项目中被规划使用

因此，最合理的方式是先把关键链路跑通，再逐步补齐深度分析功能。
